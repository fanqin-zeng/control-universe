# Wiki讨论式内容生成工作流

## 概述

本技能定义了一套多角色讨论框架，用于生成和优化控制理论wiki课程内容。内容通过四个层面的角色结构化讨论产出，确保内容兼具学术深度、工程实用性、教学质量和可读性。

## 角色体系

详见 [personas.md](./personas.md)。

### 教授团队（4人）— 理论根基

| 角色 | 姓名 | 专长领域 | 核心职责 |
|------|------|----------|----------|
| 经典控制教授 | **陈控** | 传递函数、频域分析、根轨迹、PID | 从物理直觉出发，建立工程感觉 |
| 现代控制教授 | **林矩** | 状态空间、最优控制、卡尔曼滤波 | 强调数学结构与理论优雅性 |
| 鲁棒/非线性教授 | **卫韧** | 鲁棒控制、非线性系统、自适应控制 | 连接理想与现实，处理不确定性 |
| 应用数学教授 | **方数** | 线性代数、微分方程、优化、概率 | 揭示控制理论背后的数学本质 |

### 工程团队（3人）— 落地实践

| 角色 | 姓名 | 专长领域 | 核心职责 |
|------|------|----------|----------|
| 机电控制工程师 | **周联** | MATLAB/Python控制器设计、汽车/无人机/机器人控制 | 硬件约束、跨域调试、工程代码 |
| 仿真工程师 | **何仿** | Simulink/Python仿真、可视化、验证 | 仿真环境搭建、场景验证、结果可视化 |
| 规划算法工程师 | **吴规** | 轨迹规划、路径优化、任务分配 | 代表控制系统的"甲方"，定义需求 |

### 教学支持（2人）— 质量保障

| 角色 | 姓名 | 专长领域 | 核心职责 |
|------|------|----------|----------|
| 助教 | **孙助** | 习题设计、内容翻译、易错点总结 | 把教授的话"翻译"给学生，设计练习 |
| 教务管理员 | **郑核** | 教学质量审查、一致性检查、事实核查 | 确保风格统一、代码可运行、知识无幻觉 |

### 可视化设计（1人）— 图文呈现

| 角色 | 姓名 | 专长领域 | 核心职责 |
|------|------|----------|----------|
| 技术可视化设计师 | **苏绘** | 技术插图、信息图表、可视化策略 | 决定何时用AI生成概念图、何时用动态图表组件 |

**苏绘的可视化策略（v1.3）**：

本项目的可视化分为两种场景，使用不同的技术方案：

| 场景 | 判断标准 | 技术方案 | 说明 |
|------|----------|----------|------|
| **代码演示** | 用代码将抽象概念具体化，展示计算过程、算法流程、数据验证，输出文本或图表 | `<JupyterNotebook>` 组件，静态输出即可（文本/表格/图表） | 重点是"让代码说话"，读者不需要调参 |
| **交互探索** | 展示参数变化对系统特性的影响，需要读者自行探索 | React 交互组件（ECharts + useECharts hook） | 重点是"拖动看变化"，必须有可调控件 |

**交互组件设计规范**：
- 使用 ECharts 渲染图表，配合 `useECharts` hook
- 固定坐标轴范围（避免拖动时坐标轴缩放导致视觉混乱）
- 禁用动画（`animation: false`），保证拖动时即时响应
- 控件类型不限于滑块，可根据需要选择：滑块、按钮组、下拉菜单、开关等
- 组件放在 `components/wiki/` 目录，命名如 `xxx-explorer.tsx`

**决策流程**：
```
这段内容需要可视化吗？
├── 否 → 纯文字/公式
└── 是 → 读者需要调参探索吗？
    ├── 否 → <JupyterNotebook> 静态输出（文本/表格/图表）
    └── 是 → React 交互组件（<XxxExplorer>）
```

> **v1.3 原则**：ipywidgets 在本项目的轻量级 Jupyter 服务器上不可用（无法渲染 widget）。所有交互需求必须用 React 组件实现。

## 讨论流程

### Phase 1: 内容规划

```
触发：确定要编写/优化的课程主题
参与者：教授团队 + 工程团队 + 轮值领域专家

1. 陈控：该主题在经典控制中的定位和直觉解释
2. 林矩：该主题的数学结构和现代控制视角
3. 卫韧：实际系统中的挑战和鲁棒性考量
4. 方数：所需的数学基础和关键定理
5. 周联：工程实现中的关键难点和硬件约束
6. 吴规：上游规划对该控制模块的需求和接口
7. 轮值专家：该主题在真实应用场景中的典型问题
8. 共识：确定教学目标、前置知识、核心难点、应用案例方向
```

### Phase 2: 内容生成

```
触发：内容规划完成
参与者：全员

第一轮 — 概念讲解：
1. 教授团队依次讲解核心概念的理论和数学
2. 周联/何仿补充工程实现和仿真验证
3. 吴规补充需求侧视角和应用场景

第二轮 — 学生反馈：
4. 小初提出理解困难和基础疑问
5. 李稳追问理论联系和深层逻辑
6. 赵工要求实际案例和工程意义
7. 钱锐挑战边界条件和推广可能

第三轮 — 调整完善：
8. 孙助总结学生的典型困惑，建议补充说明
9. 教授和工程团队根据反馈调整讲解
10. 何仿提供仿真结果或可视化辅助说明
```

### Phase 3: 内容审校

```
触发：初稿完成
参与者：全员分工审校

教授团队审校（学术准确性）：
- 陈控：物理直觉是否正确，工程例子是否恰当
- 林矩：数学推导是否严谨，符号是否一致
- 卫韧：是否讨论了局限性和实际约束
- 方数：数学表述是否准确，定理引用是否正确

工程团队审校（实践可行性）：
- 周联：代码是否可运行，工程参数是否合理，Python 代码是否已转为 JupyterNotebook 组件
- 何仿：仿真是否可复现，可视化是否准确，notebook cell 拆分是否合理
- 吴规：需求描述是否准确，接口定义是否清晰

教学支持审校（教学质量）：
- 孙助：习题是否覆盖核心知识点，难度梯度是否合理；答案是否完整、推导是否正确
- 郑核：教学风格是否统一、术语是否一致、是否存在知识幻觉、代码是否全部可运行；习题和答案是否一一对应
- **郑核—fix-logs 回归检查**：查阅 `.qoder/fix-logs/INDEX.md`，确认本次编写/修改的课程或章节是否有历史修复记录（例如交互组件坐标轴固定、禁用动画等），避免重犯已修复的问题

学生审校（可读性）：
- 小初：初学者能否跟上主线
- 赵工：工程师能否直接应用
```

### Phase 4: 内容定稿

```
触发：审校意见汇总完成
参与者：郑核主持，教授团队确认

1. 郑核汇总所有审校意见，标记优先级
2. 教授团队确认学术内容修改
3. 工程团队确认代码和工程内容修改
4. 孙助确认习题、答案和补充说明
5. 郑核最终签发：风格统一、无矛盾、无幻觉、代码可运行
6. 输出MDX格式的课程内容
7. 在交付记录文件中打勾：更新 .qoder/delivery-tracker.md 对应课程的 checklist
```

> **Phase 4 完成后必须更新交付记录**。郑核负责在 `.qoder/delivery-tracker.md` 中找到对应课程，将 `[ ]` 改为 `[x]`。

## 输出格式规范

讨论产出的最终内容应为MDX格式，遵循以下结构：

```mdx
---
title: "课程标题"
description: "一句话描述"
---

# 课程标题

## 引言
（从实际问题或直觉出发，引发兴趣）

## 核心概念A
（分节讲解，包含数学推导和物理解释）
（代码就近嵌入：在相关概念讲解后立即给出 JupyterNotebook 验证/演示）

## 核心概念B
（同上，代码紧跟对应概念）

## 实例与案例
（具体数值例子或工程应用，可包含综合性代码演示）

## 深入讨论
（进阶内容、前沿话题、与其他章节的联系）

## 小结
（关键要点回顾）

## 习题
（所有习题放在同一个小节，不按难度分级）

## 答案
（对应习题的完整解答，包含关键推导步骤和最终结果）
```

> **v1.3 代码嵌入规则**：不再设置独立的"代码实现"和"仿真验证"章节。代码应紧跟在其说明的概念旁边，让读者"学一个概念，立刻看到代码验证"。综合性演示代码可放在"实例与案例"节中。

> **v1.3 可视化选择规则**：
> - **代码演示场景**（用代码将抽象概念具体化）：使用 `<JupyterNotebook>` 组件，静态输出即可（文本/表格/图表），不需要交互
> - **交互探索场景**（展示参数变化对系统特性的影响）：必须使用 React 交互组件（如 `<XxxExplorer>`），配合 ECharts 和 useECharts hook，提供滑块/按钮等控件让读者自行调参
> - 禁止在 JupyterNotebook 中使用 ipywidgets（本项目轻量级服务器不支持 widget 渲染）
> - 交互组件设计规范：固定坐标轴范围、禁用动画、组件放在 `components/wiki/` 目录

## 使用方式

当需要生成或优化某课内容时：

1. 确认课程主题（参考 `content/catalog.ts`）
2. 确定本轮参与的轮值领域专家
3. **按Phase 1-4流程展开讨论，一次会话里完整完成**
4. **讨论过程完整记录**，保存至 `docs/discuss-log/course-[termNum]/[chapNum-chapName]/[lessonNum-lessonName].md`；其中`termNum`除非用户指定，使用当前同目录下已有的最大termNum，意思是当前的学期计数；`chapNum`是当前章节在全部章节中的顺序号；`lessonNum`就是当前课程在当前章节中的顺序号
5. 郑核完成最终审校
6. 输出MDX格式内容，写入对应的 `content/<chapter>/<lesson>.mdx`

## 数学基础章节规则

课程设有独立的"数学基础"章节（`content/math/`），与其他所有章节正交，供所有章节交叉引用。

**规则**：在编写任何课程内容时，如果遇到需要较多篇幅解释的数学概念（如复数、线性代数、微分方程等），且该概念不属于当前课程的核心主题，则：

1. 不在原地展开完整讲解，而是用一两句话交代直觉含义，然后引用数学基础章节的对应课程
2. 在 `content/math/` 下新建或引用已有的课程，以"假设读者只有高中数学水平"为起点编写
3. 引用格式：`> 📐 本文用到了复数的基本概念，详见 [复数基础](/math/complex-numbers)。`

这样做的目的是保持每篇课程的聚焦性，同时让数学基础薄弱的读者有完整的补课路径。

## 注意事项

- 讨论应自然流畅，避免生硬的说教感
- 学生的疑问应真实反映该水平学习者的典型困惑
- 角色之间的观点可以有分歧，通过讨论达成共识
- 数学推导要完整，不跳步
- 物理直觉和数学严谨性并重
- 每个概念都要有"为什么需要它"的动机说明
- 所有代码必须可运行（郑核负责验证）
- **所有跨行 Python 代码必须使用 `<JupyterNotebook>` 组件嵌入**，不得使用 ` ```python ` 代码块。公共导入和配置放入 `setupCode`，逻辑相关的代码放入同一个 cell，可视化代码可独立成 cell。MATLAB 代码仍使用普通代码块。（周联、何仿负责生成，郑核负责验证格式）
- **v1.3 — 代码就近嵌入**：不再设置独立的"代码实现"和"仿真验证"章节。每段代码应紧跟在其说明的概念旁边，让读者"学一个概念，立刻看到代码验证"。综合性演示代码可放在"实例与案例"节中。（何仿负责规划代码位置，郑核负责检查）
- **v1.3 — 可视化双轨制**：代码演示用 `<JupyterNotebook>`（静态出图），交互探索用 React 组件（ECharts + useECharts）。**禁止使用 ipywidgets/interact**。交互组件必须固定坐标轴、禁用动画。（苏绘负责设计，何仿负责实现，郑核负责验证）
- 所有应用场景必须来自真实工程问题（轮值专家负责确认）
- 术语和风格必须全课程一致（郑核负责检查）
- 每节课必须同时包含"习题"和"答案"两个小节，答案需给出关键推导步骤，不能只给最终结果（孙助负责设计，郑核负责核查答案正确性）
