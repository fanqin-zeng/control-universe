# Wiki讨论式内容生成工作流

## 概述

本技能定义了一套多角色讨论框架，用于生成和优化控制理论wiki课程内容。内容通过四个层面的角色结构化讨论产出，确保内容兼具学术深度、工程实用性、教学质量和可读性。

## 角色体系

详见 [personas.md](./personas.md)。

### 教授团队（4人）— 理论根基

| 角色 | 姓名 | 专长领域 | 核心职责 |
|------|------|----------|----------|
| 经典控制教授 | **陈控** | 传递函数、频域分析、根轨迹、PID | 从物理直觉出发，建立工程感觉 |
| 现代控制教授 | **林矩** | 状态空间、最优控制、卡尔曼滤波 | 强调数学结构与理论优雅性 |
| 鲁棒/非线性教授 | **卫韧** | 鲁棒控制、非线性系统、自适应控制 | 连接理想与现实，处理不确定性 |
| 应用数学教授 | **方数** | 线性代数、微分方程、优化、概率 | 揭示控制理论背后的数学本质 |

### 工程团队（3人）— 落地实践

| 角色 | 姓名 | 专长领域 | 核心职责 |
|------|------|----------|----------|
| 机电控制工程师 | **周联** | MATLAB/Python控制器设计、汽车/无人机/机器人控制 | 硬件约束、跨域调试、工程代码 |
| 仿真工程师 | **何仿** | Simulink/Python仿真、可视化、验证 | 仿真环境搭建、场景验证、结果可视化 |
| 规划算法工程师 | **吴规** | 轨迹规划、路径优化、任务分配 | 代表控制系统的"甲方"，定义需求 |

### 教学支持（2人）— 质量保障

| 角色 | 姓名 | 专长领域 | 核心职责 |
|------|------|----------|----------|
| 助教 | **孙助** | 习题设计、内容翻译、易错点总结 | 把教授的话"翻译"给学生，设计练习 |
| 教务管理员 | **郑核** | 教学质量审查、一致性检查、事实核查 | 确保风格统一、代码可运行、知识无幻觉 |

### 可视化设计（1人）— 图文呈现

| 角色 | 姓名 | 专长领域 | 核心职责 |
|------|------|----------|----------|
| 技术可视化设计师 | **苏绘** | 技术插图、信息图表、可视化策略 | 决定何时用AI生成概念图、何时用动态图表组件 |

**苏绘的可视化策略**：

| 图表类型 | 适用场景 | 实现方式 |
|----------|----------|----------|
| 数据曲线图（阶跃响应、Bode图等） | 需要交互、参数变化 | 已有动态组件（`StepResponseSlider`、ECharts） |
| 概念示意图（电路图、机械系统、框图） | 需要直观展示物理系统 | AI生成图片 → `public/images/` |
| 数学可视化（相平面、根轨迹） | 需要精确数学关系 | ECharts/自定义组件 |
| 流程/架构图 | 需要展示逻辑关系 | AI生成或Mermaid |

### 轮值角色

| 角色 | 说明 |
|------|------|
| **领域应用专家**（轮值） | 根据课程主题匹配：化工过程、自动驾驶、导航、电力电子、航空航天等。确保应用案例来自真实工程问题 |

### 学生团队（4人）— 学习视角

| 角色 | 姓名 | 水平 | 核心作用 |
|------|------|------|----------|
| 入门学生 | **小初** | 大三本科生，初学控制 | 暴露基础盲区，提出"笨问题" |
| 进阶学生 | **李稳** | 研一，基础扎实 | 追求理论深度，串联知识 |
| 工程师学生 | **赵工** | 有实践经验，理论偏弱 | 要求实际意义，拒绝空中楼阁 |
| 天才学生 | **钱锐** | 博三，数学功底强 | 挑战假设，提出前沿视角 |

## 讨论流程

### Phase 1: 内容规划

```
触发：确定要编写/优化的课程主题
参与者：教授团队 + 工程团队 + 轮值领域专家

1. 陈控：该主题在经典控制中的定位和直觉解释
2. 林矩：该主题的数学结构和现代控制视角
3. 卫韧：实际系统中的挑战和鲁棒性考量
4. 方数：所需的数学基础和关键定理
5. 周联：工程实现中的关键难点和硬件约束
6. 吴规：上游规划对该控制模块的需求和接口
7. 轮值专家：该主题在真实应用场景中的典型问题
8. 共识：确定教学目标、前置知识、核心难点、应用案例方向
```

### Phase 2: 内容生成

```
触发：内容规划完成
参与者：全员

第一轮 — 概念讲解：
1. 教授团队依次讲解核心概念的理论和数学
2. 周联/何仿补充工程实现和仿真验证
3. 吴规补充需求侧视角和应用场景

第二轮 — 学生反馈：
4. 小初提出理解困难和基础疑问
5. 李稳追问理论联系和深层逻辑
6. 赵工要求实际案例和工程意义
7. 钱锐挑战边界条件和推广可能

第三轮 — 调整完善：
8. 孙助总结学生的典型困惑，建议补充说明
9. 教授和工程团队根据反馈调整讲解
10. 何仿提供仿真结果或可视化辅助说明
```

### Phase 3: 内容审校

```
触发：初稿完成
参与者：全员分工审校

教授团队审校（学术准确性）：
- 陈控：物理直觉是否正确，工程例子是否恰当
- 林矩：数学推导是否严谨，符号是否一致
- 卫韧：是否讨论了局限性和实际约束
- 方数：数学表述是否准确，定理引用是否正确

工程团队审校（实践可行性）：
- 周联：代码是否可运行，工程参数是否合理
- 何仿：仿真是否可复现，可视化是否准确
- 吴规：需求描述是否准确，接口定义是否清晰

教学支持审校（教学质量）：
- 孙助：习题是否覆盖核心知识点，难度梯度是否合理
- 郑核：教学风格是否统一、术语是否一致、是否存在知识幻觉、代码是否全部可运行

学生审校（可读性）：
- 小初：初学者能否跟上主线
- 赵工：工程师能否直接应用
```

### Phase 4: 内容定稿

```
触发：审校意见汇总完成
参与者：郑核主持，教授团队确认

1. 郑核汇总所有审校意见，标记优先级
2. 教授团队确认学术内容修改
3. 工程团队确认代码和工程内容修改
4. 孙助确认习题和补充说明
5. 郑核最终签发：风格统一、无矛盾、无幻觉、代码可运行
6. 输出MDX格式的课程内容
```

## 输出格式规范

讨论产出的最终内容应为MDX格式，遵循以下结构：

```mdx
---
title: "课程标题"
description: "一句话描述"
---

# 课程标题

## 引言
（从实际问题或直觉出发，引发兴趣）

## 核心概念
（分节讲解，包含数学推导和物理解释）

## 实例与案例
（具体数值例子或工程应用）

## 代码实现
（MATLAB/Python代码，必须可运行）

## 仿真验证
（仿真结果和可视化）

## 深入讨论
（进阶内容、前沿话题、与其他章节的联系）

## 小结
（关键要点回顾）

## 习题
（分难度等级：基础/进阶/挑战）
```

## 使用方式

当需要生成或优化某课内容时：

1. 确认课程主题（参考 `content/catalog.ts`）
2. 确定本轮参与的轮值领域专家
3. 按Phase 1-4流程展开讨论
4. 讨论过程完整记录
5. 郑核完成最终审校
6. 输出MDX格式内容，写入对应的 `content/<chapter>/<lesson>.mdx`

## 数学基础章节规则

课程设有独立的"数学基础"章节（`content/math/`），与其他所有章节正交，供所有章节交叉引用。

**规则**：在编写任何课程内容时，如果遇到需要较多篇幅解释的数学概念（如复数、线性代数、微分方程等），且该概念不属于当前课程的核心主题，则：

1. 不在原地展开完整讲解，而是用一两句话交代直觉含义，然后引用数学基础章节的对应课程
2. 在 `content/math/` 下新建或引用已有的课程，以"假设读者只有高中数学水平"为起点编写
3. 引用格式：`> 📐 本文用到了复数的基本概念，详见 [复数基础](/math/complex-numbers)。`

这样做的目的是保持每篇课程的聚焦性，同时让数学基础薄弱的读者有完整的补课路径。

## 注意事项

- 讨论应自然流畅，避免生硬的说教感
- 学生的疑问应真实反映该水平学习者的典型困惑
- 角色之间的观点可以有分歧，通过讨论达成共识
- 数学推导要完整，不跳步
- 物理直觉和数学严谨性并重
- 每个概念都要有"为什么需要它"的动机说明
- 所有代码必须可运行（郑核负责验证）
- 所有应用场景必须来自真实工程问题（轮值专家负责确认）
- 术语和风格必须全课程一致（郑核负责检查）
