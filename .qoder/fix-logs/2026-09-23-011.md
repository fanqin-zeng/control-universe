# Fix Log 011 - Jupyter Notebook Kernel ID Collision

**Date**: 2026-09-23  
**Documents**: `components/wiki/jupyter-notebook.tsx`（影响所有含多个 `<JupyterNotebook>` 的课程页面）  
**Type**: BUG (Negative case)  
**Summary**: 同一页面上的多个 notebook 会生成相同的 kernel id，导致它们共用一个内核命名空间，互相覆盖变量并报出与本页代码无关的 ValueError

## Problem

在 `nonlinear/feedback-linearization` 页面（含 4 个 `<JupyterNotebook>`）点击"▶ 全部运行"时，Notebook 2-4 报出：

```
ValueError: not enough values to unpack (expected 4, got 2)
ValueError: x and y must have same first dimension, but have shapes (801,) and (1200,)
```

这两个错误单独运行任一 notebook 时都不出现，且报错的形状/元组长度与出错 cell 的代码不匹配——说明变量来自**别的 notebook**。

## Root Cause

kernel id 由组件实例自己的 `useRef` 计数器生成：

```tsx
const nbCounter = useRef(0);              // 每个实例都是独立的 0
const id = `nb-${Date.now()}-${nbCounter.current++}`;
```

`useRef` 是**每实例**状态，所以每个 notebook 的计数器都从 0 开始，id 实际退化为 `nb-<时间戳>-0`。同一页面的 4 个 notebook 在同一次渲染中挂载，时间戳相同 → **4 个组件拿到同一个 id**。

服务端 `scripts/jupyter_server.py` 以 id 为键管理内核（`kernels[nid] = (km, kc)`），并且 `_handle_create` 对已存在的 id 直接**覆盖注册**、`_handle_execute` 按 id 取内核。于是 4 个 notebook 的代码全部跑进同一个内核、同一个命名空间：

- Notebook 2 定义的 `run(a, x0, t_end, kv)` 覆盖 Notebook 4 的同名函数 → 解包 4 元组时拿到 2 元组
- Notebook 2 的 `t`（801 点）与 Notebook 3 的 `t`（1200 点）互相覆盖 → 绘图形状不匹配
- React 卸载时的 `deleteNotebook(id)` 会顺手关掉别的 notebook 正在用的内核

单个 notebook 的页面不受影响，因此这个 bug 在只有一两个 notebook 的旧课程里从未暴露。

## Fix

把计数器提到模块作用域，保证同页面 id 唯一：

```tsx
// Module-level so notebooks mounting in the same millisecond never share a kernel id.
let nbSeq = 0;
function newNotebookId() {
  return `nb-${Date.now()}-${nbSeq++}`;
}
```

挂载时的 `useEffect` 与 `reset()` 两处创建 id 的代码统一改用 `newNotebookId()`；随之删除不再使用的 `useRef` 导入。

## Lessons Learned

- **正案例**：任何"每实例唯一"的标识符都不能用 `useRef` 计数器生成——`useRef` 的初值在每个实例上都一样。需要跨实例唯一时用模块级变量或 `useId()`。
- **负案例**：以客户端传入的 id 作为服务端字典键时，`_handle_create` 应当检测 id 已存在并复用/报错，而不是静默覆盖注册。这个 bug 之所以难查，是因为报错出现在"受害者" notebook 里，而根因在另一个 notebook 的注册上。
- **诊断技巧**：当报错的形状/元组长度与出错代码对不上时，第一反应应该是"命名空间被污染"，而不是"我的代码写错了"。逐个运行 vs 同时运行的差异是判断污染的最快方法。
- 该 bug 与课程内容无关，属于共享组件缺陷；此后任何含 ≥2 个 notebook 的课程都不会再复现。

## 遗留观察（已于同日修复）

页面刷新属于硬导航，React 卸载清理不会执行，因此旧内核不会被 DELETE，服务端 `kernels` 字典持续增长（本次调试后累积到 19 个，每个内核是一个独立的 Python 进程）。

修复方式（`scripts/jupyter_server.py`）：

- 新增 `last_used` 时间戳与后台守护线程 `reap_idle_kernels()`，空闲超过 `JUPYTER_IDLE_TIMEOUT`（默认 1800 s，设 0 关闭）的内核自动 shutdown；巡检周期 `JUPYTER_REAP_INTERVAL`（默认 60 s）。
- 正在执行 cell 的内核记在 `busy` 集合里，回收时跳过，避免长仿真被中途杀掉。
- 所有对 `kernels` / `last_used` / `busy` 的读写加 `threading.Lock`（HTTP 主线程 + 回收线程并发）。
- `_handle_create` 遇到重复 id 时先关掉旧内核并打印 WARNING（Fix-011 的服务端兜底：两个 notebook 永远不会共用命名空间）。
- `/health` 额外返回 `idle_timeout` 与每个内核的 `idle_seconds`，便于观察。

配套的前端恢复（`components/wiki/jupyter-notebook.tsx`）：内核被回收后再点运行会收到 404，此时抛 `KernelGoneError` → 自动重建内核并**从第 1 个 cell 重放到当前 cell**（新命名空间没有前面 cell 定义的变量，只重跑当前 cell 必然 NameError）。请求用的 id 改存 `idRef`，因为恢复过程中 state 里的旧 id 已失效。

实测（`JUPYTER_PORT=8897 JUPYTER_IDLE_TIMEOUT=3 JUPYTER_REAP_INTERVAL=1`）：7 s 的 cell 在 3 s 阈值下正常跑完（busy 保护）；空闲后 `kernels` 由 1 归 0 并打印 `Recycled idle kernel r3`；回收后 execute 返回 404。浏览器端注入一次 404 后，请求序列为 `execute(404) → DELETE → create → execute ×2`，NB2 的 cell 1/2 输出均正确、无 Traceback。
