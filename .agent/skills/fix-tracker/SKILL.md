# Wiki修复追踪技能

## 概述

本技能用于在每次wiki内容优化会话中，记录用户提出的反馈和修复内容。每次修复以"正负案例"形式归档——记录修复前的问题（负案例）和修复后的方案（正案例），形成可检索的经验库。

## 文件架构

```
.agent/
  skills/fix-tracker/
    SKILL.md              # 本文件：记录格式 + 工作流 + 归因口径与回顾机制
  fix-logs/
    INDEX.md              # 索引（实测为正序：001 在顶、最新在底；B8 前本文件写的是"倒序"）
    YYYY-MM-DD-NNN.md     # 每次修复的独立记录文件（NNN 是全局序号，不是当天序号）
```

### 分离原则

- **SKILL.md**：定义记录格式、工作流与归因回顾机制。**B8 起它同时是归因口径的权威副本**（`semester-02-plan.md` §3.7 M5 只有三行字段定义，回填结果与回顾表都在本文件），所以"技能定义不变"这句自 B8 起作废
- **INDEX.md**：所有修复条目的索引，便于快速检索
- **YYYY-MM-DD-NNN.md**：每次修复的详细内容，按日期+序号命名

这样做的目的：
1. SKILL定义与数据分离，技能升级不影响历史记录
2. 每次修复独立成文件，避免单文件膨胀
3. INDEX.md只存摘要，快速浏览不需打开每个文件

## 记录格式

### INDEX.md 条目格式

```markdown
| # | 日期 | 文档 | 章节 | 类型 | 归因角色 | 摘要 |
```

- **`#`**：**全局**递增序号（001…018…），不是当天序号。既有 18 条实测符合全局序号，但本文件《工作流》第 1 步此前写的是"当天最大序号 +1"，按那句在 2026-09-24 会算出 001 并与 `2026-09-22-001.md` 撞名——B8 已更正该步
- **类型**：`NEG`(负案例) / `POS`(正案例) / `BOTH`(正负对比) / `BUG`(功能或渲染故障)。`BUG` 是 B8 **追认**的既有值：实测 18 条中 `BUG` 13 条、`BOTH` 5 条、`NEG`/`POS` 各 0 条，也就是说 B8 之前 72% 的数据在用未声明的枚举值
- **归因角色**（B8 起新增列，插在 `类型` 与 `摘要` 之间）：本该拦住它但没有的角色，取自 `wiki-discussion/personas.md` 的 22 人池。每个单元格必须带下列标记之一，因为两种情形的改进方向不同：
  - `（B1 新设）` = 事故发生时该角色**尚未设立** → 改进方向是**新增角色**（B1 已做，见《归因回顾机制》§3）
  - `（清单缺项）` = 事故发生时该角色**已存在、但检查清单里没有这一条** → 改进方向是**补清单**（不是加人）
  - `※Qn` = 该条归因存在跨文件冲突，裁定与依据见《归因回顾机制》对应小节
- **摘要**：一句话描述，**≤120 字**。B8 之前本文件两处自相矛盾——《文件架构》的注释写"每条≤120字"、本节写"≤80字"；现统一为 120。实测 18 条中 13 条超 80 字、8 条超 120 字，**超出的 8 条属存量债务、不回改**（B8 范围只有本文件与 INDEX.md 两个文件）

### 单条修复记录格式 (YYYY-MM-DD-NNN.md)

```markdown
---
date: YYYY-MM-DD
doc: content/chapter/lesson.mdx
section: 章节标题
type: NEG | POS | BOTH | BUG
tags: [交互组件, 可视化, 内容补充, ...]
---

# 修复摘要：一句话标题

## 问题（负案例）

用户指出的具体问题。原文哪里不好、缺什么、错什么。

**用户原话**：<逐字引用，含标点。无用户原话时写明触发来源，例如"浏览器实测报错"或"npm run check 报 FAIL">

## 修复方案（正案例）

做了什么改动、为什么这样做。

## 涉及文件

- `path/to/file1.tsx` — 新建/修改说明
- `path/to/file2.mdx` — 修改说明

## 经验提炼

可复用的经验，供后续类似修复参考。

## 角色归因（B8 起必填）

归因角色：<本该拦住它但没有的角色>
拦截缺口：<该角色的检查清单里缺了哪一条>
清单更新：<已写入 SKILL.md / personas.md 的具体条目；若未写入则填"待补">
```

**三个归因字段的写法要求**（照 `semester-02-plan.md` §3.7 M5，逐字引入上面的字段名与占位符）：

- **归因角色**：只能填 `wiki-discussion/personas.md` 里真实存在的角色名（22 人具名池，不含 14 类轮值专家——轮值专家是领域知识来源，不持有检查清单，因此无法成为"拦截缺口"的归属）。一条 fix 允许填两个角色，但必须写明主责与协查，例如"苏绘（主责·视觉规范）+ 何仿（协查·仿真出数）"
- **拦截缺口**：必须写成**可加进清单的一句话**，不能写"没注意到""不够仔细"。判据 = 这句话能不能直接变成一个 `- [ ]` 勾选项；不能就还没找到缺口
- **清单更新**：必须给出**落点**（哪个文件的哪一节 / 哪一条），例如"`wiki-discussion/SKILL.md`《前端交付硬门槛（B6 起）》§1 第 5 项"或"`personas.md` 柯验清单 A 组【必查陷阱 2】"。**填"待补"是合法的，但"待补"必须在学期末回顾时清零**（见《归因回顾机制》§2 触发条件）

**为什么归因要落在 fix-log 而不是讨论日志**：fix-log 记录的是**已经漏出去、被用户或实测抓到的**问题，讨论日志记录的是**流程内拦下来的**问题。只有前者能回答"谁的清单缺了哪一条"，所以 M5 的闭环挂在 fix-log 上。

### 既有 14 篇详情文件的格式实测（B8）

B8 在写入三字段之前先量了既有文件的实际形态——**结论是本节声明的模板只被 2 篇遵守（14%）**，所以三字段不能只加在模板里，否则机制会写在无人使用的格式上（与 B6 实测出九项硬门槛里 2 项"在纸面上存在、在实践里空转"同族）：

| 格式 | 特征 | 篇数 | 条目 |
|------|------|------|------|
| A · 本节声明的模板 | YAML frontmatter + `## 问题（负案例）`/`## 修复方案（正案例）`/`## 涉及文件`/`## 经验提炼` | **2** | 001、005 |
| B · 英文节名（**当前主流**） | `# Fix Log NNN - 标题` + `**Date**`/`**Documents**`/`**Type**`/`**Summary**` 四行 + `## Problem`/`## Root Cause`/`## Fix`/`## Verification`/`## Rule` | **9** | 006、011、012、013、014、015、016、017、018 |
| C · 正负案例变体 | `# Fix-NNN: 标题` + `## 负面案例：`/`## 正面案例：`/`## 教训`（002、003）或 `## 现象`/`## 根因分析`/`## 修复方案`/`## 教训 / 规则`（004） | **3** | 002、003、004 |

**三字段在三种格式里的落点（B8 起的硬要求）**：

- 格式 A：新增 `## 角色归因（B8 起必填）` 一节，放在 `## 经验提炼` 之后（即上面的模板）
- 格式 B：新增 `## Attribution` 一节，放在 `## Rule` 之后，**三行字段名仍用中文**（`归因角色：` / `拦截缺口：` / `清单更新：`）——字段名是 M5 逐字规定的，不随节名翻译，否则跨文件 grep `归因角色` 会漏掉这批
- 格式 C：新增 `## 归因` 一节，放在 `## 教训` 之后，同样用中文三行字段名
- **既有 14 篇不回填详情文件**（与 wiki-discussion B4「既有 11 篇讨论日志不回填」同型）：B8 的范围是两个文件，改 14 篇详情属越界；这 18 条的归因由 `INDEX.md` 的新列 + 本文件《归因回顾机制》§4 的回填明细表承载，**详情文件只在将来因其他原因被打开修改时顺手补上**

**另一处格式漂移的后果（B8 顺手修）**：格式 B 与 C 都**没有**承载用户原话的位置，实测 `用户原话`/`用户反馈`/`用户指出` 只出现在 002 与 003 两篇（2/14）。而本技能《概述》的第一句就是"记录用户提出的反馈"——主流格式把这个技能存在的理由丢掉了。故上面的模板在 `## 问题（负案例）` 下新增 `**用户原话**：` 必填行，并允许写"无用户原话 + 触发来源"（fix-011/015/017 这类是构建或浏览器实测抓到的，本来就没有用户原话，逼着编一句反而造假）。

## 工作流

### 记录修复（用户提出反馈并修复后）

1. **确定修复编号**：读 INDEX.md，取**全表最大 `#` 加 1**（全局序号，不是当天序号）。文件名里的日期是记录当天、`NNN` 是全局序号
2. **创建修复记录文件**：`.agent/fix-logs/YYYY-MM-DD-NNN.md`，按《单条修复记录格式》写全，含 `## 角色归因（B8 起必填）`
3. **填归因三字段**：先从 `wiki-discussion/personas.md` 的 22 人具名池里找出"本该拦住它但没有的角色"，再写拦截缺口与清单更新。**三字段缺任一项 → 郑核不得关闭该 fix 条目**（见《注意事项》）
4. **更新 INDEX.md**：在表格**底部追加**新条目。实测既有 18 条是**正序**（001 在顶、018 在底），B8 之前本文件写的是"顶部插入、最新在前"，与实际相反，已按实际更正
5. 如果修复涉及新建组件，在记录中标注组件路径
6. **把缺口变成清单项**：该 fix 暴露的缺口要同步写进 `personas.md` 对应角色清单或相应 SKILL.md，然后把落点回填到第 3 步的"清单更新"字段——**这一步做完，`清单更新：待补` 才允许清零**

### 查阅历史

1. 读 INDEX.md 获取所有修复概览（B8 起可按"归因角色"列筛出某个角色的全部漏检）
2. 按 tags 或 doc 筛选感兴趣的条目
3. 打开对应的详细记录文件查看完整内容

### 学期末归因回顾（B8 起）

按下方《归因回顾机制》执行：统计归因分布 → 判定是否触发"改清单"或"拆职责" → 把回顾表与修改记录写进本文件。

## 归因回顾机制（B8 起）

> **来源**：`semester-02-plan.md` §3.7 M5。**执行者**：郑核（教务管理员，持有签发与关闭权）。**产物**：本节 §3 之后按学期追加的回顾小节。**为什么要有这一节**：B1 设立 6 个新角色的唯一依据就是 §0.3 的归因数据（18 条里 7 条落在职责真空区），但那次归因是**一次性手工做的**；没有回顾机制，下一次就无法回答"新角色到底拦住了什么"，也无法回答 plan §5.3 最后一项与风险表里那条"新角色是纸面角色、实际不发挥作用"。

### §1 回顾表格式

每学期末追加一个小节 `### 第 N 学期归因回顾（YYYY-MM-DD）`，内含这张表：

```markdown
| 归因角色 | 归因条数 | 类别分布 | 是否触发拆分 | 已采取的清单更新 |
|---------|---------|---------|------------|----------------|
```

- **归因角色**：只列**被归因过**的角色（0 条的角色另列在表下的"零拦截名单"里，不占表行）
- **归因条数**：该角色作为**主责**的条数；协查条数写在括号里，例如 `4（协查 1）`。**计数口径见 §2**
- **类别分布**：按 §4 的归因类别列，形如 `前端/MDX 工程 3 · 数值一致性 1`
- **是否触发拆分**：`否` / `是（改为 …）` / `是（清单第 N 条拆成 …）`
- **已采取的清单更新**：给出落点（文件 + 节名 + 条目号）；仍为"待补"的必须写 `待补（原因）`

### §2 触发条件（可判定，不靠印象）

**触发条件 T1 · 改清单或拆职责**：**同一角色**在**连续 3 条**同类问题上都是归因对象 → 必须修改该角色的检查清单，或拆分其职责，**并把修改记录写入本文件**（§1 的表 + 一段说明）。三个词的操作定义：

- **同一角色**：按主责计。协查不计入 T1 的连续计数（否则"苏绘+何仿"这类双归因会把两个人的计数同时撑大）
- **连续**：按 INDEX.md 的 `#` **序号连续**，不看日期、不看中间是否夹着别的角色的条目。序号连续 = 同一个交付批次内反复漏同一类，这才说明清单没起作用
- **同类**：同一**归因类别**（§4 的类别列）。新增类别时必须先在 §4 登记再使用，否则"同类"无法判定

**触发条件 T2 · 人设无效**：某角色**整学期零拦截**（既没被归因过任何一条漏检，其清单也没有任何一条在讨论日志或 fix-log 里留下可核查的拦截记录）→ 说明该人设是纸面角色，**应删除或改造**，并把裁定写入本文件。这条对应 plan §5.3 的最后一项与风险表"新角色是纸面角色"那一行。

**触发条件 T3 · 待补清零**：学期末回顾时，`清单更新：待补` 的条目数必须为 **0**。仍有"待补"→ 该 fix 条目**不得关闭**，并在回顾表里逐条列出待补原因与责任人。

**不得触发的情形**：单条 fix 归因给某角色**不构成**任何触发；T1 要求的是**连续 3 条同类**，不是"累计 3 条"。累计口径会让高频出场的角色（如秦构，凡是前端课都在场）被反复误判。

## 注意事项

- **归因三字段是关闭 fix 条目的前置条件（B8 起）**：新增 fix-log 时 `归因角色` / `拦截缺口` / `清单更新` 必须填全，**缺任一项则郑核不得关闭该 fix 条目**。这与 wiki-discussion 的签发闸门同型——郑核不重算数值、不重跑对比，只核三件事：字段是否填全、归因角色是否在 22 人具名池里、"清单更新"是否给了**可核查的落点**（文件 + 节名 + 条目号）。`清单更新：待补` 是合法值，但学期末回顾时必须清零（《归因回顾机制》§2 的 T3）
- **归因角色只能从 `wiki-discussion/personas.md` 的 22 人具名池里选**，不含 14 类轮值领域专家——轮值专家是领域知识来源、不持有检查清单，因此无法成为"拦截缺口"的归属
- **不要把归因写成检讨**：`拦截缺口` 必须能直接变成一个 `- [ ]` 勾选项。写"没注意到""下次仔细点"等于没归因，郑核应退回重填
- **既有 14 篇详情文件不回填三字段**（B8 的范围是两个文件，改 14 篇属越界）；这 18 条的归因由 INDEX.md 的"归因角色"列 + 《归因回顾机制》§4 的回填明细表承载。将来因其他原因打开某篇详情文件时，顺手把三字段补上
- 每次修复只记录**最终方案和决策理由**，不记录讨论过程
- 经验提炼要具体可操作，不要空泛总结
- INDEX.md 超过 100 条时考虑按章节分卷；**分卷时"归因角色"列必须保留**，否则回顾机制失去数据源
- 修复记录使用中文撰写。节名沿用既有习惯即可（实测 9/14 篇用英文节名 `Problem` / `Root Cause` / `Fix` / `Verification` / `Rule`，正文仍是中文），但**三行归因字段名必须用中文**（`归因角色：` / `拦截缺口：` / `清单更新：`），字段名是 §3.7 M5 逐字规定的，翻译掉会让跨文件 grep 漏掉这批
