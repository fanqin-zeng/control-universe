# 新写一节课程

先读并执行 [学期3共同流程](../wiki-discussion/references/semester-03-core.md)，再执行下面的新写专用步骤。团队、发言纪律和 M1–M5 不变。

## 准备：确认教学空缺

从 `.agent/semester-03-plan.md` 选定唯一课程 ID，核对全局 checklist 和源路径。有任一被沿用的正文就改用重构技能，不能把旧文搬过来宣称从零新写。若计划模式因新正文出现而失效，先更新计划并记录原因。

读前后课、术语表、符号表及相关 fix 记录。区分“必需先修已交付”“本课补足的局部定义”“延伸阅读”；列出读者完成本课后能回答的问题，避免百科式罗列。入口条件不足时登记阻塞，不在一个对话中补写先修课。

## Phase 1：先设计能学会的路径

先形成一页设计合同：读者起点 → 问题 → 学习目标 → H2 → 算例/可视化 → 练习 → 验收证据。由学生挑战起点假设，再由教师确认 H2；不要从生成一篇长文开始。

至少设计一个贯穿问题和一个失败或边界例；不必每节都造独立大工程。理论课区分定义、定理、证明与直觉，工程课先给可检验需求和预算。算法课给输入、输出、训练/推理接口及停止条件，避免代码先于问题。

## Phase 2：先跑通最小例，再扩写

先独立运行小算例并确定可视化默认值，再把证据写成讲解；三轮讨论仍完整进行。正文数字来自实际输出，不根据“应该如此”提前填值。新模型、新数据集或实验环境要给来源、版本、计算成本及轻量替代方案。

正文遵循动机 → 直觉 → 严谨表达 → 算例 → 误区/边界 → 练习。学生反馈必须触发有位置的修改；不得以“读懂了”替代检验。避免借相邻未交付课省略关键定义。

## Phase 3–4：验证首次可学、首次可跑

除共同门槛外，检查：从声明的起点能独立学完；全部新概念有定义；例题与习题没有未讲方法；notebook 从干净 kernel 顺序执行；组件默认状态就是主算例；新路径/导航/前后课可达。

共同流程的完整日志、签发、checklist、master提交与推送全部完成后才算交付。新课只有一节，后续课的草案只能登记为计划，不能顺带签发。
