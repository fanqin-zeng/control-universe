# Fix Log 016 - rk4 的抽稀输出让"按索引算时间"差一个 keep 倍

**Date**: 2026-09-25  
**Documents**: `components/wiki/phase-plane-explorer.tsx`（Van der Pol 极限环周期读数）  
**Type**: BUG (Negative case: 组件读数与正文/Notebook 差 20 倍，违反 Fix-014)  
**Summary**: `rk4()` 为了控制点数会把积分结果按 `keep = round(steps/1200)` 抽稀后再返回，返回数组的下标**不是积分步**。Van der Pol 分支用"过零事件下标 × (T/steps)"换算时间，等于把每个抽稀点当成一个积分步，周期读数小了 `keep` 倍（实测 0.319 s，真值 6.381 s）

## Problem

`PhasePlaneExplorer` 切到 Van der Pol 时，读数区显示"实测周期 0.319033 s"，而正文与 Notebook 1 给的是 6.380676 s，小 μ 渐近式 6.381360 s。组件与正文相差整整 20 倍——读者只会认为其中一个是错的。

## Root Cause

`rk4()` 内部 `steps = max(400, round(T*60))`，但只把 `i % keep == 0` 的点 push 进返回数组（`keep = max(1, round(steps/1200))`）。T = 400 时 steps = 24000、keep = 20，返回 1201 个点，相邻点间隔是 `T/1200 = 1/3 s` 而不是 `T/24000`。

过零检测遍历的是**返回数组**，事件下标 `i` 是抽稀后的下标；换算时间却乘了 `T/steps`（积分步长），于是每个事件的时间被压缩 20 倍。第一版修复把 `def.T` 换成 `Tlong` 只修掉了 2 倍的另一半错误，剩下的 20 倍来自这里。

## Fix

用返回数组自身的长度反推抽稀步长：`dtStored = Tlong / (long.length - 1)`，事件时间 = `(i - 1 + frac) * dtStored`。这样无论 `keep` 取几、T 取多少，换算都自洽，不再依赖 `rk4` 内部的步数公式。

## Verification

浏览器实测（`/nonlinear/phase-plane`，切到 Van der Pol，默认 μ = 0.5）：

- 修复前：实测周期 0.319033 s，"小 μ 渐近式相对误差 95.001%"；
- 修复后：实测周期 **6.380664 s**，振幅 x₁ ∈ [−2.002181, 2.002147]、峰峰值 4.004328，相对渐近式 6.381360 的误差 **0.011%**——与 Notebook 1 的 6.380676 / 0.011% 一致（末位差异来自事件插值网格）。

## Rule

**从抽稀/降采样序列里提时间量时，时间基准必须从序列本身推**（`T/(len-1)`），不能引用积分器内部的步长常量。凡是"下标 × dt"的写法，先问一句：这个下标是积分步还是输出点？
